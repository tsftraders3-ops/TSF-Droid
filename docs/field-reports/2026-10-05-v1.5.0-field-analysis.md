# Field Analysis Report — v1.5.0 real-usage session (2026-10-05)

**Source data:** 7 chat exports (`workspace/Exports/*.json`) + 13 agent-created files + 1 empty
directory, zipped by the user after ~1 day of real use of the v1.5.0 release APK
(versionCode 15, `mimo-v2.6-flash-free` on OpenCode Zen free tier).
**Sessions covered:** 6 unique sessions (one was exported twice, 02:30 and 10:31), 30 user turns,
100+ tool calls, spanning 2026-10-04 15:54 → 2026-10-05 11:08 local time.
**Analyst method:** fresh clone at `3ad9bb6`, full re-read of the harness/agent loop, tool
execution, and persistence/export layers (3 deep exploration passes), then a turn-by-turn
forensic read of every export, then cross-referencing each observed failure with the exact
code path that produced it. Every claim below cites the chat export + the code location.

---

## 0. Executive summary

The chat-export feature did its job: every JSON parsed, every field the debugging loop
needed was present, and this report exists because of it. The agent's *failures* are now
fully visible — and they are not random. They cluster into **eight root-cause families**,
and every one of them is fixable in code, not model-hope:

1. **False success claims** — the app told the user a cab was booked when no booking
   tool exists or ran (`humanizeGoalDone` fabricates completion after ASK_USER-only plans).
2. **Deterministic file creation is structurally broken** — the fallback content engine
   writes hardcoded filenames (`Documents/report.pdf`, `Documents/document.txt`,
   `Documents/data.json`), ignores user-requested names, captures model *narration*
   as document content, and ships unfilled `[placeholder]` templates.
3. **Unguarded answer shapes leak raw internals** — raw `web_search {"query":...}` tool
   syntax, the harness's own `I used web_search(...) to work on this.` stub, and a whole
   ```json {"speech": ...}``` wrapper all reached the user verbatim; the existing gates
   (echoed-listing, monologue) match different shapes.
4. **The NeedsInput loop is a trap** — a UI-automation plan with unfilled params burned
   28 minutes, ignored four explicit "stop" commands, double-persisted every user reply,
   and ended with `Action 'TAP' is not registered` (the planner invented an action name
   that the validator never fixed).
5. **Storage is split-brained** — WRITE_FILE → the user's SAF folder, CREATE_PDF → the
   app-private workspace, CREATE_DIRECTORY → SAF. Result: an empty `MarketReports/`
   in the user's folder, the gold PDF in `Android/data`, and 12/12 WRITE_FILE turns
   with **no artifact card**.
6. **Intent routing misfires** — a *question* ("where are export chats saved?") became a
   file-write that **silently overwrote the user's Python script**; a calendar+weather+email
   ask hit a screen-reading *alias* twice and then sent the full private query to public
   web search.
7. **Multi-deliverable asks get one deliverable** — 4-file ask → 1 file (wrong name, wrong
   extension); 2-file ask → 0 files; "both files" → 1 file + a 45k-char inline dump in chat.
8. **The export omits the input side** — no CHAT/AGENT mode, no per-turn prompt/config, and
   `usage.latencyMs` that under-counts turn wall time by ~9 minutes on expansion turns —
   several root-cause conclusions below are *weaker* than they should be because of this.

**Priority for the next session:** P0-1 through P0-8 below (each has a "fix direction").
Fixing families 1–4 addresses the trust-destroying failures; family 5 the file-location
confusion; family 6 the routing damage; family 8 makes the *next* field report sharper.

## 3. Issue catalog — P0 (trust-destroying; fix first)

### P0-1. False success claim: "Your cab is booked" (no booking tool exists or ran)

**Evidence** (chat-021218, 16:25:36→16:26:39): user asked "book cab for yesterday 5pm wait
no I mean tommrow 5am". Plan = 1 step: ASK_USER (Auto-approved). The assistant asked for
destination/pickup/app. User replied "destinatin is kolkata , my location". Final saved
message: **"Your cab is booked for tomorrow at 5 AM from your current location to
Kolkata."** The only tool call in the turn is `ASK_USER (33.3s, ok)`. No booking action
exists in the 131-action registry. When the user asked "what platform did u used to book
cab?" the model confessed: *"I don't have a platform to report — I jumped ahead earlier.
No booking was actually completed on Uber, Ola, or anywhere else."*

**Root cause (code):** `AgentLoop.speakAndSaveSummary` (AgentLoop.kt:3753–3857) treats
"all steps succeeded" as "goal accomplished". An ASK_USER step that returns an answer is a
SUCCESS step, so the summary ladder reaches `cannedSuccessSummary`/`humanizeGoalDone`,
which asserts completion of the *goal* ("Your cab is booked…") — not of the *steps*.
Nothing verifies that the executed steps are semantically capable of the goal (there is no
BOOK_CAB action; the plan was pure questioning).

**Fix direction:** (a) `humanizeGoalDone` must not assert goal completion for plans whose
steps contain no world-changing action (ASK_USER/CHAT-only plans → "I've noted your
answers", never "done"); (b) add a goal-capability check at plan time: if the goal's verbs
(book/order/pay/send) have no corresponding registered action, SAY SO at proposal time
instead of executing a plan that can only ask questions; (c) the summary ladder needs a
"what actually happened" pass that lists executed actions and their outcomes verbatim
before any completion sentence.

### P0-2. Deterministic content-engine produced a one-sentence "research report" PDF

**Evidence** (chat-033518, 02:31:41→02:36:44): user asked for deep research on 3B/7B LLMs
**"compile a comprehensive report called ondevice_llm_benchmark_2026.md … extract all the
raw performance numbers into a table and save it as llm_perf_metrics.csv"**. The turn
produced ONE step: `CREATE_PDF filePath=Documents/report.pdf`, with dispatched
`content = "I'll first check the environment and whether I can gather any real data."` —
the model's mid-work narration. The 201KB PDF contains **exactly two lines**: the raw user
query as title, and that sentence. Neither requested file was created. 5 minutes spent.

**Root cause (code):** `synthesizeExecutablePlan` (AgentLoop.kt:1943–2077) — the
deterministic planner that fires when the model's plan defers — builds a single
WRITE_FILE/CREATE_PDF step with a hardcoded filename (`"Documents/report.pdf"` at
1991–1997/2068) and a content-engine call whose `FILE:` first line is stripped (2063–2066).
Here the engine's output began with the model's narration and ended there; there is **no
content-quality gate** (minimum length, narration detection, placeholder detection) on
what gets written, and **no filename extraction** from the goal. The narration-as-content
capture also indicates the engine prompt's output contract is not enforced by parsing.

**Fix direction:** content gate before write: reject content < N chars, content matching
narration patterns ("I'll first…", "Let me…"), and unfilled `[placeholder]` brackets
(see P0-3); parse the requested filename(s) from the goal (regex on `called X`,
`named X`, `save it as X`, `save as X` — including extension) and fall back to a
slugified goal + correct extension by kind (md for reports, csv for tables);
multi-deliverable goals (P1-6) need multi-step synthesis, not one hardcoded step.

### P0-3. Unfilled placeholder template shipped as the deliverable PDF

**Evidence** (chat-111835, 10:32:31→10:36:21): gold-market ask. The searches found real
numbers (₹14,780 24K / ₹13,538 22K, Moneycontrol), yet the dispatched PDF content was:
`COMPARISON TABLE / 24K | [today 24k price] | [last week 24k price] | [calc %] …
SOURCES / 1. [Financial news site 1]` — a template with every value an unfilled bracket.
Additionally the requested "set a reminder for 5pm tomorrow" was **silently dropped**
(no step, no mention), and the CALCULATE step failed because the model passed prose inside
the expression (`…* 100, using prices found in steps s1 and s2`).

**Root cause (code):** same content engine as P0-2: it emits a *template* and no stage
fills it with the gathered step results. `PlanValidator`'s quote-assist (which appends
CHECK_STOCK for metals, PlanValidator.kt:220–237) ran **after** the PDF step in plan
order, so even that data arrived too late. CALCULATE's expression param has no
sanitization (no extraction of the arithmetic from surrounding prose).

**Fix direction:** template-fill pass over the content before CREATE_PDF: substitute
`[…]`/`{…}` placeholders from prior step results (the harness has the data in
context); if a placeholder cannot be filled, **fail the write** and fall back to
chat-answer, never ship brackets. CALCULATE param sanitizer: strip everything outside
the leading arithmetic expression (stop at first `,`+space or lowercase prose).
Goal-coverage check at plan time: every imperative clause in the goal maps to a step or
an explicit "can't do X" note (the reminder was droppable because nothing checks it).

### P0-4. Raw tool-call syntax delivered as the final answer (17-minute turn)

**Evidence** (chat-033518, 02:38:23→02:55:14): cost/rate-limit analysis ask. 20 tool
calls (9 fetch failures, 4 of them the same dead `ai.google.dev` URL retried 4×), thinking
245s, usage 70,071 tokens / latency 67.2s. The delivered 12,274-char answer **begins
with six raw lines** `web_search {"query": "Gemini 1.5 Flash pricing input output tokens
per 1M"}web_search {"query": …}` before the (good) analysis text.

**Root cause (code):** the model emitted its tool intentions as *text* alongside real
tool_calls; `HarnessLoop.narrationWithCalls` (HarnessLoop.kt:284–286) executes the calls
and appends narration to context, but when that same text survives into the final
TurnResult content nothing filters it. The echoed-listing guard (292–304) only matches
"Top web results"/"Web results for" prefixes; the monologue guard's opener list
(`need to|gonna|i'm going to|…`, lines 70–97) does not match `web_search {` or
`I used web_search(`. The expansion pass ("Expanded to full length" step) then *rewrote*
the answer at full length starting from that polluted context, cementing the syntax into
the final text.

**Fix direction:** an answer-hygiene pass on final content: strip/rewrite leading
`<tool_name> {...}` runs (the app knows its own tool names — regex per advertised tool);
extend the echoed-output guard to trigger on any line matching
`^(web_search|fetch_url|write_file|create_pdf|read_file|list_files|shell)\s*[({]`;
and feed the expansion a cleaned transcript (tools-as-syntax lines removed) so the
rewrite doesn't inherit them.

### P0-5. The harness's own round-stub delivered as the answer

**Evidence** (chat-021145, 01:57:10→01:58:06): "about the financial market" (follow-up
in a news session). 4 tool calls (2 searches ok, 2 fetches failed on reuters/cnbc), then
the final saved message was exactly: **`I used web_search({"query": "Reuters stocks oil
dollar yields October 4 2026 close"}) to work on this.`** — the harness's context-stub
sentence (HarnessLoop.kt:1021–1031), delivered to the user as the turn's answer.

**Root cause (code):** the model's final content echoed the stub style ("I used X to
work on this."); `isMonologueShaped` (70–97) doesn't list `I used`, doesn't fire; the
give-up nudge only triggers on price-like asks; nothing else inspects final content
shape once tools have run. The user received zero information after 56 seconds.

**Fix direction:** extend the final-content shape gate: after tools ran, content that
matches the stub pattern (`^I (used|ran|called) <action>\(`…), or is < 15 words with no
sentence-final punctuation plus new-data, gets one FINAL_ANSWER_NUDGE re-ask (the
mechanism already exists — it's the opener list that's incomplete). Same family as
P0-4: one `AnswerShape` validator instead of three ad-hoc regex lists.

### P0-6. Raw `{"speech": …}` JSON wrapper delivered verbatim

**Evidence** (chat-021218, 16:28:54): "need regx that maches indian phone number…". The
delivered message is a fenced ```json block: `{"speech": "Here are two regex options…",
"type": "SIMPLE", "action": null, "params": {}}` — with all `\n` escapes intact, the
answer unreadable in the UI. No thinking, no usage, no activity steps.

**Root cause (code):** this is a CHAT-mode streamed reply (badge/model null → the
plain streaming path). The wrapper-form CHAT-slop gates live only in
`parsePlanFromLlmResponse` (AgentLoop.kt:4079–4205) — i.e., the *plan* path. The
streaming path (`executeSimpleQuery` L1257–1297) saves any non-blank content as-is; its
only text inspection is `formatStreamedReply`'s "Error streaming" prefix check (4063).
A model answering in its plan-JSON dialect in chat mode sails through.

**Fix direction:** route streamed replies through the same sanitizer family: detect
JSON-envelope answers (content parses as JSON with any of speech/response/text/action
keys, optionally fenced), extract the speech/response string, deliver *that*; if
extraction fails, deliver a graceful "the model answered in the wrong format" message
rather than the raw blob. This mirrors the wrapper-form gate that already exists for
plans — reuse `replyRefusesGoal`'s JSON-sniffing utilities.

### P0-7. A question misrouted into a file-write that silently overwrote the user's script

**Evidence** (chat-021145, 02:08:53→02:10:14): "can you tell me the location in device
where the export chats are saved" → plan: WRITE_FILE `Documents/document.txt` with a
hallucinated, **WhatsApp-flavored** "Where are my exported chats saved" document
("WhatsApp Exports folder… Files app on iPhone…"). The answer the user got was
`File saved at document.txt`. This **overwrote** the `Documents/document.txt` that held
their `scrap_titles.py` script from 02:03:10 (the script's content survives only inside
the export JSON's toolCalls params). The actual question was never answered — the real
answer (`workspace/Exports/`, shareable via the sheet) appears nowhere.

**Root cause (code):** three stacked failures. (a) Intent routing: a "where/can you
tell me" question reached a WRITE_FILE plan — the artifact-goal heuristics
(`goalWantsArtifact` ARTIFACT_WORD list) don't distinguish "explain X" from "create X"
when file-ish words appear. (b) `StorageWorkspaceProvider.writeFileLocal`
(StorageWorkspaceProvider.kt:327–336) overwrites via `writeText` with **no collision
detection, no rename, no confirmation** — the deterministic default `document.txt` is a
collision magnet because it's the same hardcoded name every time (see P1-1).
(c) The generated content is ungrounded (no source-grounding for a factual support
question), so it hallucinated third-party app behavior.

**Fix direction:** collision guard at the storage layer (auto-rename `document-2.txt` +
tell the model, or refuse and ask); question-vs-task classifier before plan synthesis
(interrogatives about app behavior → CHAT/knowledge path, and the app's own real
answer for "where are exports saved" is knowable in-code: inject it as grounded
context); when a generated support document contradicts the app's actual behavior,
that's a prompt-side fix: give the planner a small "app facts" block (export location,
workspace path, SAF behavior).

### P0-8. The 28-minute NeedsInput trap (TAP not registered, "stop" ignored)

**Evidence** (chat-111835, 10:40:27→11:08:28): flipkart/amazon automation ask (open app,
wait, read screen, tap search bar, search, scroll twice, screenshot). Sequence observed:
19 minutes of silence (planning + slow accessibility execution: `OPEN_APP` Flipkart,
`OPEN_APP` Amazon, `TYPE_TEXT "mechanical keyboard wireless"` 44.9s, `OPEN_APP` Chrome,
`SCROLL` 182.5s, `TYPE_TEXT <flipkart search URL>` 132.6s, `TAP` ✗, `TYPE_TEXT` same
URL again 64.5s, `KEY ENTER`); then a cycle of prompts — "I need the searchText to
complete this. Text to find the field" → user "what do u want" → "I need the content to
complete this. Content to type" → user "ooo" → "I need the direction… forward/backward"
→ user "forward" → "I need the searchText" (loop) → user **"stop don't need to do
anything" ×2** → still "I need the content…" → user "kjn" ×3 → final answer:
**`Action 'TAP' is not registered in ActionDispatcher`**. Every user reply was
double-persisted (see P1-4). The requested screenshot was never taken. The automation
opened Chrome and typed a URL into it instead of staying in the app.

**Root cause (code):** five stacked failures.
(a) **Planner param-laziness**: the goal text contained every param ("tap on the search
bar" → CLICK_TEXT text; "search for 'mechanical keyboard wireless'" → TYPE_TEXT content;
"scroll down twice" → direction+count), but the emitted plan had steps with *empty*
required params; `resolveParameters` (ActionSequenceExecutor.kt:57–81) only substitutes
prior-step results, never goal text.
(b) **No cancel-escape**: `resolveNeedsInput` (AgentLoop.kt:3459, 3619) feeds *any* user
reply into the missing param slot — including "stop don't need to do anything", which
was consumed as param text and the plan kept running. Nothing checks
stop-intent/cancellation lexically or via a Stop affordance on the prompt.
(c) **Unknown action survived validation**: the planner invented `TAP`; real names are
`CLICK_TEXT/CLICK_ID/CLICK_COORDINATES` (AccessibilityActions, schema at
ActionSchema.kt:1187–1235). `PlanValidator.validateAndFix` "auto-fixes unknown actions"
but has no TAP→CLICK_TEXT mapping (`ActionAutoMapper` only maps `TAP_ENTER→PRESS_ENTER`),
so it reached dispatch and died as UnknownAction — *after* the 19-minute execution phase.
(d) **Cryptic prompt copy**: "I need the searchText to complete this. Text to find the
field" exposes internal param names instead of asking "Which text should I tap?".
(e) **MAX_NEEDS_INPUT_PROMPTS=5** per action, but with several broken steps the loop
cycled across steps (searchText→content→direction→searchText), so the cap never bit.

**Fix direction:** param extraction from goal at plan-build/validation time (the
planning prompt must be told: fill every param from the goal or mark the step
ASK-worthy); hard cancel lexicon in the needs-input answer path ("stop", "cancel",
"never mind", "don't", "quit" → abort the whole plan with an honest summary);
alias map TAP→CLICK_TEXT (+ PRESS/CLICK variants); prompt copy rewritten to
user-language with the param's *meaning*; a per-plan prompt budget (not per-step)
plus a visible progress line during execution (the 19-min silence); fail UnknownAction
at *validation*, not dispatch.


## 4. Issue catalog — P1 (functionality broken in a visible way)

### P1-1. Hardcoded default filenames; user-requested names ignored

**Evidence:** three independent incidents. (a) "write a python script **call
scrap_titles.py**" (chat-021145 02:03:10) → saved as `Documents/document.txt`. (b) The
4-file architecture ask (chat-033518 03:22:20) — explicit `agent_architecture_spec.md`,
`tools_definition.json`, `agent_config.yaml`, `mock_tool_dispatcher.py` — → one file
`Documents/data.json` whose content is the *markdown architecture spec* (invalid JSON).
(c) Both deep-research PDFs (02:31 and 03:14) → hardcoded `Documents/report.pdf`, twice,
so the second **overwrote the first**; the user manually renamed one to keep both
(the zip's `"file was namedreportpdf but I change its.pdf"` is the user's rescue).

**Root cause (code):** `synthesizeExecutablePlan` hardcodes `Documents/report.pdf`
(AgentLoop.kt:1991–1997, 2068) and equivalents for text/JSON; it never parses the
user's requested filename. The chat-mode fallback `ToolCallBridge` create_pdf branch
derives names from title with `[^a-zA-Z0-9]+→_` (ToolCallBridge.kt:74–88), which also
mangles extensions. `resolveFile` performs zero filename normalization
(StorageWorkspaceProvider.kt:143–204).

**Fix direction:** goal-filename parser (`called|named|save (it )?as|titled` + extension
preservation); correct extension by content kind; overwrite guard (P0-7) makes even the
fallback safe; never write markdown into a `.json` name.

### P1-2. Storage split-brain: WRITE_FILE → SAF folder, CREATE_PDF → app-private workspace

**Evidence:** all 12 WRITE_FILE results read "File saved at **<name only>**" (the SAF
branch's message, StorageWorkspaceProvider.kt:318) — files landed in the user's chosen
SAF folder (that's why they could zip them). All 4 CREATE_PDF results read "PDF created:
File saved at **/storage/emulated/0/Android/data/com.tsfdroid.ai/files/workspace/**…"
(`writeBinaryFile`, which has no SAF branch). `CREATE_DIRECTORY MarketReports` went to
SAF, so the gold PDF landed in `workspace/MarketReports/` while the user's
`MarketReports/` stayed **empty** (physically confirmed: the zip's MarketReports/ is
empty). The user had to mine `Android/data` to retrieve the PDFs.

**Root cause (code):** `writeBinaryFile` (388–397) never got the SAF routing that
`writeFile` (305–325) has — the v1.5.0 export QA never exercised a custom SAF folder.

**Fix direction:** route binary writes through the same `shouldUseCustomFolder`
dispatch (SAF `createFile` with the right mime), or always write to workspace and
*copy* to SAF; one canonical answer to "where do files go" surfaced in the UI + docs.

### P1-3. WRITE_FILE artifact cards never fire (12/12 missing) with a SAF folder

**Evidence:** in all 7 exports, every CREATE_PDF message carries an `artifact` card;
**zero** WRITE_FILE messages do — including good turns (workout_routine.md,
merge_json.py, conversation_notes.md…). One turn even says "open it from the card
below" (agent_frameworks.md, chat-023029 02:21:55) with no card attached.

**Root cause (code):** `emitArtifactCardIfNeeded` (AgentLoop.kt:2723–2774) takes the
path from `dataMap["path"] ?: params["filePath"]`. WRITE_FILE's Success returns only a
message string (no `path` key), so the card re-resolves the *relative* filePath against
the local workspace — but the file is in the SAF folder → `!file.exists()` → silently
skipped (2749–2751). CREATE_PDF returns an absolute path key (added in v1.4.0), so its
cards work.

**Fix direction:** WRITE_FILE Success should return the resolved URI/absolute path the
way CREATE_PDF does; the card validator should accept SAF document URIs, not only
`java.io.File` existence.

### P1-4. User replies double-persisted during needs-input waits

**Evidence:** 10 duplicate consecutive USER rows across two exports — every reply sent
while a plan waited on needs-input/ask_user ("what do u want", "ooo", "forward",
"stop don't…", "kjn", "sms hi to the number 123"…): distinct UUIDs, ~15–30 ms apart,
identical text (chat-111835 pairs at 10:59:21.066/10:59:21.081 etc.; chat-021230
16:20:54.883/.899).

**Root cause (code):** the needs-input answer path inserts the user's message into the
conversation AND the normal send path inserts it too (both `handleNeedsInput` delivery
and `processQuery`'s pending-ask reply path run for the same send). Not a rendering
artifact — both rows carry independent ids in the DB.

**Fix direction:** single-writer for parked-plan replies (idempotent insert keyed on
pending-ask id, or suppress the generic insert when the turn is consumed by
resolveNeedsInput).

### P1-5. SMS to a literal phone number impossible

**Evidence** (chat-021230, 16:17:55→16:21:52): "using sms msg 123, hi" → "I couldn't
find '123'. What's their phone number?"; "sms hi to **the number 123**" ×3 (with
double-persist) → same "I couldn't find 'sms hi to the number 123'" — the whole query
was treated as a contact *name* lookup. Four attempts, four failures, user gave up.

**Root cause (code):** the SEND_SMS flow resolves the recipient through the contacts
DAO only; no digit-string detection (an all-numeric token or `+91…` pattern should
short-circuit straight to number-sending). The repeated message also suggests the
retry path re-entered the same broken resolution.

**Fix direction:** regex `^\+?\d[\d\s-]{6,}$` → bypass contact lookup entirely; fall
back to asking for the number with an explicit "send to 123?" confirmation instead of
"I couldn't find '…'".

### P1-6. Multi-deliverable goals collapse to zero or one deliverable

**Evidence:** 4-file ask → 1 file (P1-1b); 2-file ask ("…benchmark_2026.md … save it as
llm_perf_metrics.csv") → 0 requested files, 1 garbage PDF (P0-2); "both files" → 1 file
+ the entire second file dumped inline into a 45,368-char chat message that opens
"Here are both files, complete and ready to use." (false — `AgentKeepAliveManager.kt`
was never written; the thinking trace shows the model knew it had two files to write).

**Root cause (code):** the deterministic synthesizer emits a *single*-step plan by
design; the model-driven plan path wrote one file then answered. `AnswerEngine`
has a raw-dump detector (`looksLikeRawDump`, AnswerEngine.kt:134–148) but it targets
*web listings* — a ```markdown fence of a file body passes; nothing penalizes
"here are both files" claims when the disk disagrees.

**Fix direction:** multi-artifact goal detection (count distinct requested filenames →
emit N steps); post-turn artifact audit: every filename promised in the reply text
must exist on disk (the collector already validates existence — invert it into a
claim checker); cap inline file dumps in the answer (link the card, quote a summary).

### P1-7. Intent misroutes: alias capture + full-query web search

**Evidence** (chat-111835, 10:39:21/10:39:39): the calendar+weather+email+headlines+
briefing+Spotify ask (6 sub-tasks, all capabilities exist: calendar actions,
GET_WEATHER, READ_EMAILS-class actions, ADD_NOTE, PLAY_MUSIC) was answered twice with
`badge=alias` "Reading your screen and saving the important details." (a screen-read
alias fired; no tool calls; no result), then a WEB_SEARCH whose query was the **entire
403-char private request** ("my calendar events for today, fetch the current weather
forecast for kolkata, read my last 5 unread emails…") — a privacy leak into a public
search engine — returning unrelated articles. Final answer: honest total-failure.
The user re-sent the request once and got the same path twice.

**Root cause (code):** the alias shortcut list (AgentLoop.kt:902–963) matched
keyword(s) in the query (likely "read … save") before the intent classifier could route
a compound goal; the alias path announced and no-op'd. The fallback then collapsed
6 tasks into one WEB_SEARCH with the raw text as the query (no keyword extraction —
contrast `repairSearchQuery` which exists but wasn't applied here).

**Fix direction:** alias short-circuits must be **verb-phrase anchored** ("read my
screen", not bare "read/save") and must yield to multi-intent detection (split on
", and … then" clause structure); never send a raw first-person request to
WEB_SEARCH (extract entities/keywords first); log+surface alias hits so silent
no-ops are visible.

### P1-8. Self-refusal: "file tools aren't available in this session" + missing switch guidance

**Evidence** (chat-023029, 02:22:27 and 02:24:17): "make a phone_prices.csv" →
"I couldn't save a file this session, so here's the CSV content … If you'd like, re-run
the request from a session with file access"; "save it as ai_policy_update.txt" →
auto-approved plan **WEB_SEARCH only** (artifact goal deferred), answer: "file tools
aren't available in this session". Both offers lacked the mandated line "Switch to
Agent mode (the toggle at the top) and I'll do it for you." Less than two minutes later
in the same session, "save the notes from our conversation into a file" → WRITE_FILE
succeeded — so capability was present and the earlier claims were false for the mode.

**Root cause (code):** the ai_policy plan deferred the artifact goal and
`planDefersGoal` (PlanResponseSanitizer.kt:387–395) did **not** swap it (the
`goalWantsArtifact` word list missed "save it as X" or the plan's WEB_SEARCH step
satisfied a check it shouldn't); the phone_prices turn shows the model *believing* it
lacks write (chat-mode advertising or a stale belief) and nothing corrects a
false-capability claim in the final answer. The prompt hardening that mandates the
switch-mode sentence is not enforced on this path.

**Fix direction:** artifact-word list gains `save (it )?as|write .* to a file|make a
\.(csv|txt|md|json)`; a final-answer claim check ("file tools aren't available" while
`write_file` is advertised → append the switch line or auto-offer mode flip);
consider surfacing the current mode + its write capability in the composer UI so the
user never has to guess.

### P1-9. Silent goal-dropping inside an otherwise-good turn

**Evidence** (chat-111835 gold turn): "set a reminder for 5pm tomorrow to check gold
rates again" — no step, no mention, no reminder. The WhatsApp-to-rahul sub-goal was
asked about (ASK_USER) and user-cancelled (fine), but the reminder vanished silently.

**Root cause (code):** no goal-coverage audit; `PlanValidator` fixes steps it has,
never asks "which imperatives in the goal have no step?".

**Fix direction:** imperative-clause extraction vs step coverage at validation; any
uncovered clause gets either a step or an explicit "can't do X" line in the summary.

## 5. Issue catalog — P2 (quality/polish)

- **P2-1. PDF rendering quality** (all 3 PDFs): markdown rendered literally
  (`**bold**`, `##`, `--` rules, `|` pipe-tables as raw text), title = the raw user
  query (truncated mid-word, no cleanup), ~200KB minimum size per PDF (one-line PDF
  = 201KB — Skia embeds an unsubstituted full font per document), whitespace-only
  word wrap (long tokens clip off-page). *Cause:* `CreatePdfAction.renderPdf`
  (AdvancedControlActions.kt:241–314) is a bare `PdfDocument` text printer.
  *Fix:* strip-or-render markdown (reuse MarkdownLite's Block tree), embed a subset
  font or use system font without full embedding, sanitize titles, char-level wrap.
- **P2-2. Repeated dead-URL fetches:** 4 identical `ai.google.dev` failures (20–21s
  each ≈ 80s wasted) in one turn; `developer.android.com` ×2, `openai.com/api/pricing`
  ×2. *Cause:* no per-URL circuit breaker in the harness loop (the doom-loop guard
  hashes name+args but the model varied queries while re-fetching the same URL).
  *Fix:* failed-URL memo per turn (skip repeats with a "skipped, previously failed"
  tool result).
- **P2-3. "Running:" echo messages** expose the raw user query + internal step names
  ("Execute CHAT", "Execute ASK_USER") on every plan turn. *Fix:* humanize or fold
  into the activity trace.
- **P2-4. Thinking-text duplication:** the 16-min turn's thinking contains the model's
  plan twice with segments glued without separator ("Let me start.Let me plan this.").
  *Cause:* multiple reasoning segments concatenated by the streaming collector without
  joiner. *Fix:* join with "\n\n".
- **P2-5. `usage.latencyMs` under-reports turn time:** 17-min turn shows latency 67.2s
  (~9 min of expansion/continuation phases are not counted — they're not harness
  `provider.complete()` calls). *Fix:* record turn start/end and a phase breakdown;
  export `wallMs` alongside.
- **P2-6. Mode/config absent from the export** (input-side gap confirmed in the field):
  the phone_prices/ai_policy analysis (P1-8) had to *guess* CHAT vs AGENT mode; the
  flipkart plan's proposal/approval state is invisible (no "Running:" echo in that
  session's exports). *Fix:* persist mode + per-turn plan id/approval + model config
  snapshot in the export header per message.
- **P2-7. Alias turn with no evidence** (DND, chat-021218 16:29:58): "turn on dnd mode
  till 8am tommrow" → `badge=alias` "Got it, changing Do Not Disturb." — no tool call,
  no activity step, no end-time handling; unverifiable whether anything happened.
  *Fix:* alias path must record an activity/tool row (even a synthetic one) or not
  claim action.
- **P2-8. Session titles never auto-generate** — every export is `New Chat`
  (`chat-new-chat-*.json` ×7). *Fix:* first-turn title summarization (cheap, one call)
  or derive from first 6 words.
- **P2-9. SCROLL 182s / TYPE_TEXT 132s** — accessibility-driven execution is
  character-by-character slow. *Fix:* batched text entry via clipboard-paste strategy
  where the target supports it; investigate the SCROLL path (3 minutes for one
  scroll suggests a retry storm).
- **P2-10. `available_tool_calls.txt` says "131 actions"** while the dispatcher
  registers 142 executors / 132 schema definitions — drift between the model's tool
  list and the real registry. *Fix:* generate the doc from the schema at build time.
